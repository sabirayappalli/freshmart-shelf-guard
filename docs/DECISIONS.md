# Decisions and trade-offs

| # | Decision | Alternatives considered | Why this one | What we give up |
|---|---|---|---|---|
| 1 | **Synthetic data from an inventory *simulator***, not random rows | Public datasets (M5/Walmart, Favorita) | Public sales data has no inventory or orders, so you can't see stockouts or replay a different ordering policy. A simulator gives censored POS (like real life) **and** ground-truth demand for an honest backtest. | It's synthetic. Parameters are tuned to grocery benchmarks (≈5% OOS, ≈3% lost sales, ≈15% promo OOS), not taken from a real customer. |
| 2 | **Lakeflow Declarative Pipeline (SQL) + Auto Loader** from a UC Volume | Lakeflow Connect (SaaS/DB connectors), Zerobus push | The chain's POS/WMS/DC systems export files nightly, which is the most common grocery pattern. Auto Loader gives exactly-once incremental loads (proven: the 2nd update only read the new day's files). | Real-time shelf signals (e.g. RFID, Zerobus) would cut latency from nightly to minutes. That's the next step, not the MVP. |
| 3 | **Expectations: drop bad rows, fail on systemic defects** | Quarantine table for everything | Void reversals and missing store keys are row-level noise (dropped and counted). Negative inventory means the WMS feed is broken, so the update fails loudly. | Dropped rows aren't kept for reprocessing. A quarantine table is a small add if audit needs it. |
| 4 | **One global LightGBM model, direct multi-horizon (h = 1..7)** | One ARIMA/Prophet model per series (16k models); deep learning (TFT) | Shares signal across 16k sparse series, trains in about 6 minutes on serverless, and handles promo/holiday covariates natively. Easy to explain (feature importance). | Lower peak accuracy than a tuned TFT on long series; no hierarchical reconciliation. |
| 5 | **Train only on in-stock target days** | Train on all POS | A stocked-out day's POS shows what was *on the shelf*, not what customers wanted. Training on it teaches the model to under-forecast exactly where stockouts happen (a censoring spiral). | Fewer training rows on chronic-OOS SKUs. |
| 6 | **Promotion gate = unbiased + beats legacy overall and on promo days** | "Beat legacy WAPE by ≥10%" | Daily store-SKU demand at 5–30 units is mostly Poisson noise (WAPE floor ≈0.35–0.40). The legacy forecast's real failure is **bias**: −25% on promo days. A 10% WAPE gate measured the wrong thing (it failed at 7% while the model fixed the bias). | WAPE improvement alone looks modest, so the value story has to come from the backtest, not from accuracy. |
| 7 | **Risk = Monte Carlo of the next 3 days *under the current replenishment rule*** (WMS open POs by due day + ML demand distribution) | "Forecast > on hand + on order" (closed form) | The closed form was our first version and it **failed its calibration check (AUC 0.52)**: it ignores that the system keeps reordering and fresh items arrive next morning. Simulating the real rule gives AUC 0.81 and 75% HIGH-tier precision, and lets us re-simulate *with* the suggested order ("risk if approved"). Ranking by revenue at risk puts the promo chicken above the spice jar. | Needs WMS open-PO due dates (a realistic feed) and an approximation of the legacy rule's state (trailing average). |
| 8 | **Value via policy replay on identical demand** | Compare forecast accuracy, or A/B test in stores | Accuracy isn't money. Replaying the same 6 hold-out weeks with only the ordering rule swapped isolates the policy's effect, including the *cost* (more inventory, more shrink). Conservative: the ML policy is fed the legacy (censored) history. | Simulated, not a live store pilot. The deck proposes a 6-week, 10-store pilot to confirm. |
| 9 | **GenAI = `ai_query` in batch SQL, grounded on structured facts** | Chatbot per alert; agent that calls tools | Store managers need one sentence they trust, generated once per night for ~1,500 at-risk items (pennies). The LLM sees only the row's facts, so there's nothing to hallucinate *from*. The facts sit next to the sentence for audit. | Not interactive. Interactive questions go to Genie. |
| 10 | **Lakebase for the app (synced tables + app-owned write table)** | Query the SQL warehouse from the app | Store managers need instant reads and transactional writes (approve/override). A warehouse is the wrong engine for OLTP. Synced tables keep one source of truth in UC. The app's actions are readable back in UC through the Lakebase catalog, so Genie can answer "how many orders were approved?" | One more system to run (Autoscaling scales to zero, so cost is small). |
| 11 | **Metric view as the semantic layer for Genie *and* the app** | Write KPI SQL in each place | One governed definition of OSA, OOS rate and lost sales. Genie and the app can't disagree. | Metric views need recent DBR/warehouse versions. |
| 12 | **Row filter on risk scores by region; column mask on supplier cost** | Separate tables per region; views | Policy-as-code in UC, enforced in every engine (SQL, Genie, notebooks), with no data copies. | The app uses its service principal (HQ scope). Per-manager scoping in the app would use on-behalf-of-user auth (a documented next step). |
| 13 | **FastAPI + plain HTML front end** | React/AppKit; Streamlit | Smallest moving-parts app that still does real OLTP writes, Genie chat and charts. Easy to read in review. | Less polished component library. |
| 14 | **One DAB, one job** orchestrating land → Lakeflow → ML → GenAI → governance | Separate jobs per team | The whole journey reruns with one command, and the evidence shows every stage in one run. | In production, ingestion (nightly) and model retraining (weekly) would run on separate schedules. |

| 15 | **Score on Spark, simulate on 16k rows** | pandas groupby/apply on the driver | The first version spent ~39 min per scoring pass in single-node pandas/LightGBM on the serverless driver (diagnosed from `system.query.history`: no Spark activity for 39 min). Distributed `spark_udf` scoring + Spark aggregation brought it to **2.7 min**. | — |
| 16 | **Batch LLM with no `max_tokens` cap + an explicit non-empty quality gate** | Tight token cap to bound cost | With caps of 90 and 1,000 tokens the model returned empty strings for most rows (the budget is used before visible text). The gate (`errors + empty < 5%`) caught it and failed the task instead of publishing blank alerts. The prompt asks for one sentence, so cost stays bounded by the prompt. | Slightly less predictable per-call cost. |

## Known limitations (stated up front)

- Lost sales in `gold` are **estimated** from the in-stock run rate. The simulator shows true lost demand is about 2x higher, so the KPI is conservative.
- The backtest's ML policy uses features from the legacy (censored) history, so real-world benefit should be *higher*, not lower.
- The scope is 200 high-velocity SKUs × 80 stores. The deck states the extrapolation assumptions to the full assortment explicitly.
